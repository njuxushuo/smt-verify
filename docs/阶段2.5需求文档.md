# 阶段 2.5 需求文档：Operator Semantics 重构与阶段二结构整理

## 1. 背景与目标

阶段一和阶段二是按照开发顺序逐步实现的：

```text
阶段一：Stage 输入契约
阶段二：Symbolic Shape + Shape Constraints + Shape Reduction
```

开发顺序本身没有问题，但源码的最终组织原则不能继续按照“每完成一个阶段就新增若干 stage-specific 文件”的方式无限增长。

本项目后续应遵循以下原则：

> **阶段用于规划开发顺序，源码按长期语义职责组织。**

当前代码中已经出现第一个需要整理的点：

- `src/stage_validator.py` 中维护了一份 operator 名称集合；
- `src/shape_constraints.py` 中再次根据 `op.type` 对 `matmul / add / mul` 做分支；
- 阶段三还会继续实现这些 operator 的 tensor value symbolic semantics。

如果阶段三继续另写一套：

```python
if op.type == "matmul":
...
elif op.type == "add":
...
```

则同一个 operator 的知识会散落在多个文件中。

因此，本阶段 2.5 不增加新的验证能力，而是对阶段二代码做一次**小规模、面向长期扩展的结构重构**。

---

# 2. 本阶段目标

本阶段只完成以下两件事：

1. 建立统一的 **Operator Semantics abstraction + registry**；
2. 修复 `shape_reducer.py` 当前 constraint dedup 仅依赖 Python hash 的实现。

重构完成后：

```text
StageSpec / OpSpec
        ↓
get_operator(op.type)
        ↓
OperatorSemantics object
        ↓
shape_constraints(...)
```

阶段三继续在同一个 operator abstraction 上增加 tensor value semantics，而不是重新建立一套 operator dispatch。

本阶段不得改变阶段一、阶段二任何外部可观察行为。

---

# 3. 当前代码中需要解决的问题

当前仓库主要结构：

```text
src/
├── stage_model.py
├── stage_loader.py
├── stage_validator.py
├── shape_model.py
├── shape_constraints.py
└── shape_reducer.py
```

当前 `shape_constraints.py` 内部存在类似：

```python
if op.type not in {"matmul", "add", "mul"}:
    ...

if op.type == "matmul":
    ...
else:
    ...
```

这意味着：

```text
Operator dispatch
Operator arity
Operator shape semantics
```

都由 shape constraint builder 自己知道。

这不符合长期组织方式。

目标结构应变成：

```text
shape_constraints.py
        ↓
get_operator(op.type)
        ↓
operator.shape_constraints(...)
```

此后 `shape_constraints.py` 只负责：

- 遍历 program；
- 找到 operator；
- 获取 input/output symbolic shapes；
- 调用 operator 自己的 shape semantics；
- 汇总 constraints。

它不再知道 MatMul、Add、Mul 各自的数学 shape 规则。

# 4. 本阶段固定设计决策

## 4.1 Operator 单独使用一个源码模块

新增：

```text
src/operators.py
```

当前只有 3 个真正实现 shape semantics 的 operator，因此暂时**不要创建 `src/operators/` 目录以及每个 op 一个文件**。

即不要创建：

```text
src/operators/base.py
src/operators/matmul.py
src/operators/add.py
...
```

目前这样属于过度拆分。

当未来 operator 数量明显增多时，再将 `operators.py` 自然拆成 package。

---

## 4.2 Operator 类负责 operator-specific semantics

阶段 2.5 中，每个已实现 operator 对应一个类：

```python
MatMulOperator
AddOperator
MulOperator
```

共同继承：

```python
OperatorSemantics
```

当前类内正式实现：

```python
shape_constraints(...)
```

阶段三将在这些同一类中增加：

```text
tensor value symbolic semantics
```

但是：

> 阶段 2.5 不实现 tensor value semantics。

不要为了未来阶段提前设计复杂 symbolic tensor 类型。

---

## 4.3 Operator registry 是唯一 dispatch 入口

所有需要通过字符串 operator type 查找语义实现的代码，都必须统一调用：

```python
get_operator(...)
```

禁止在其他业务代码中继续出现：

```python
if op.type == "matmul":
...
elif op.type == ...
```

---

## 4.4 Stage input 支持集合与 Stage 2 shape 支持集合需要区分

阶段一当前允许读取：

```text
add
mul
matmul
transpose
reshape
sum
all_reduce
all_gather
reduce_scatter
```

但是阶段二只实现：

```text

```

这两个概念必须继续区分：

```text

```

表示 Stage JSON 当前允许出现的 operator 类型。

```text

```

表示当前已经存在语义实现对象的 operator。

对于：

```text

transpose
sum
all_reduce
all_gather
reduce_scatter
```

阶段一 validation 仍然通过。

阶段二调用 `get_operator(...)` 时必须抛：

```text

```

不要因为 registry 中没有实现就让阶段一拒绝这些 input。

# 6. `OperatorSemantics` 基类

定义：

```python
class OperatorSemantics:
    name: str

    def shape_constraints(
        self,
        input_shapes: tuple[tuple[z3.ArithRef, ...], ...],
        output_shapes: tuple[tuple[z3.ArithRef, ...], ...],
        context: str,
    ) -> list[z3.BoolRef]:
        raise NotImplementedError
```

要求：

- operator-specific 的 input/output 数量检查由 operator 类自己完成；
- tensor rank 检查由 operator 类自己完成；
- shape 数学关系由 operator 类自己返回；
- `shape_constraints.py` 不再知道具体规则。

当前不使用 `abc.ABC` / `@abstractmethod` 强制复杂抽象。

保持简单。

# 11. Operator Registry

在 `operators.py` 中定义：

```python
OPERATOR_REGISTRY: dict[str, OperatorSemantics] = {
    "matmul": MatMulOperator(),
    "add": AddOperator(),
    "mul": MulOperator(),
}
```

提供：

```python

    ...
```

行为：

如果存在：

```python

```

如果 `name` 属于：

```python

```

```text

all_reduce
all_gather

```

```python

```

注意：



```python

```

## 14.2 重写 `_operator_constraints`

保留函数：

```python
def _operator_constraints(
    program: ProgramSpec,
    tensor_refs: dict[str, TensorRef],
    shapes: SymbolicShapeBook,
    context: str,
) -> list[z3.BoolRef]:
```

但职责改为 orchestration。

逻辑固定为：

```text
for each op
    ↓
construct op_context
    ↓
operator = get_operator(op.type, op_context)
    ↓
resolve all input symbolic shapes
    ↓
resolve all output symbolic shapes
    ↓
operator.shape_constraints(...)
    ↓
append returned constraints
```

伪代码：

```python
for index, op in enumerate(program.ops):
    op_context = f"{context}.ops[{index}]"

    semantics = get_operator(op.type, op_context)

    input_shapes = tuple(
        shapes.shapes[tensor_refs[name]]
        for name in op.inputs
    )

    output_shapes = tuple(
        shapes.shapes[tensor_refs[name]]
        for name in op.outputs
    )

    constraints.extend(
        semantics.shape_constraints(
            input_shapes,
            output_shapes,
            op_context,
        )
    )
```

## 15.2 修复 constraint dedup

当前实现：

```python
unique: dict[int, z3.BoolRef] = {}

for constraint in constraints:
    simplified = z3.simplify(constraint)
    unique.setdefault(hash(simplified), simplified)
```

存在理论 hash collision 风险。

重构为：

```python
unique: dict[str, z3.BoolRef] = {}

for constraint in constraints:
    simplified = z3.simplify(constraint)
    key = simplified.sexpr()
    unique.setdefault(key, simplified)

return list(unique.values())
```

即使用完整 Z3 S-expression 作为 dedup key。

不要再仅使用：

```python
hash(simplified)
```

```text

├── shape_constraints(...)
└── value semantics       ← Stage 3 增加

├── shape_constraints(...)
└── value semantics       ← Stage 3 增加
```

阶段三不得再建立另一套：

```text

```

dispatch。

但本阶段不要提前定义一个不成熟的 `symbolic_execute()` 正式函数签名。

因为阶段三还需要先决定 symbolic tensor 的数据结构。

等 symbolic tensor interface 确定后，再给 `OperatorSemantics` 增加正式的 value semantics 方法。

# 27.5 必须删除的旧实现与重复内容

本次重构不是“在旧代码旁边再新增一套新结构”。

Codex 必须在完成迁移后，**删除已经被新结构取代的旧定义和旧分派逻辑**，避免仓库同时存在新旧两套实现。

以下内容必须明确清理。

## 27.5.1 `src/stage_validator.py`

删除当前文件中自己维护的 operator 集合：

```python
SUPPORTED_OPERATORS = frozenset(...)
```

重构后只允许：

```python
from .operators import DECLARED_OPERATOR_TYPES
```

并统一使用：

```python
DECLARED_OPERATOR_TYPES
```

仓库中不得同时存在：

```text
SUPPORTED_OPERATORS
DECLARED_OPERATOR_TYPES
```

两份表达相同含义的 operator 名称集合。

---

## 27.5.2 `src/shape_constraints.py`

删除当前 operator-specific helper：

```python
_same_shape_constraints(...)
```

该 helper 迁移至：

```text
src/operators.py
```

后，旧定义必须删除，不允许复制保留。

删除 `_operator_constraints(...)` 中所有 concrete operator semantics，包括类似：

```python
if op.type not in {"matmul", "add", "mul"}:
    ...

if op.type == "matmul":
    ...

else:
    ...
```

以及直接写在该文件中的：

```text
MatMul:
A[1] == B[0]
C[0] == A[0]
C[1] == B[1]

Add/Mul:
shape(A) == shape(B) == shape(C)
```

这些公式迁移到：

```text
MatMulOperator
AddOperator
MulOperator
```

之后，`shape_constraints.py` 中不得再保留副本。

最终该文件只能通过：

```python
semantics = get_operator(...)
semantics.shape_constraints(...)
```

获取 operator-specific constraints。

## 27.5.4 `src/shape_reducer.py`

删除旧 constraint dedup 实现中：

```python
hash(simplified)
```

作为唯一 identity key 的逻辑。

例如以下形式不得残留：

```python

```

统一替换为：

```python
key = simplified.sexpr()
```

旧实现必须删除，不要保留为 fallback 或 unused helper。

# 29. 本阶段完成后的长期结构原则

从本阶段起，后续实现统一遵守：

> **Stage 是开发计划，不是源码模块边界。**

新增能力前，先判断该能力属于哪个长期语义对象。

例如：

```text
MatMul value semantics
```

应加入：

```text
MatMulOperator
```

而不是创建：

```text
stage3_matmul.py
```

类似地：

```text
Shard value semantics
```

未来更适合加入 relation abstraction，而不是创建：

```text
stage4_shard.py
```

只有真正承担独立系统职责的模块，例如：

```text
parser
solver orchestration
shape reduction
lemma cache
```

才应该形成独立源码模块。

阶段 2.5 的最终目标是：

> **在不改变现有验证功能的前提下，把当前代码从“按开发阶段堆叠”调整为“按长期语义职责组织”，为阶段三及后续 operator/relation semantics 的持续扩展建立稳定结构。**
